# Tickets Service

`tickets` is the ticket-sales domain service implemented as a **Jakarta REST/JAX-RS application packaged as a WAR and deployed to WildFly**. It intentionally uses a different stack from the Spring Boot services because the educational assignment requires JAX-RS + WildFly.

The service owns three writable business collections:

- `tickets` — individual railway tickets;
- `venues` — temporary local representation of a concrete departure/run;
- `price_histories` — the authoritative history of a ticket's base price and discount.

It also maintains a read-only local projection of Inventory train-set snapshots:

- `train_sets` — logical projection from the CDC JSON document;
- `train_set_carriages` — logical projection of the carriages array;
- `seats` — logical projection of `scheme.seatPositions`.

The three Inventory projections are **not stored as separate relational tables**. They are read from `train_set_cdc.data` JSONB.

## API base path

All endpoints use:

```text
/api/v1/tickets
```

The service is a Jakarta REST application deployed as a WAR to WildFly. JSON is the only business-media type. The OpenAPI contract is `Docs/tickets_openapi.yaml`.

## Domain model

### Venue

A `Venue` is a concrete departure/run instance. The future master identifier for this object is expected to come from `schedule-service`, but that service does not exist yet, so `tickets` temporarily owns the object.

```text
id
name
train_set_id
```

`train_set_id` is the Inventory train-set identifier. `capacity` is deliberately not part of the model because the number of seats comes from Inventory.

Venue rules:

- `id` is autogenerated;
- `name` is required, non-blank and unique;
- `train_set_id` is required and positive;
- the application must verify that a corresponding Inventory snapshot is present before accepting the Venue;
- `train_set_id` must not be changed after tickets exist for that Venue;
- `name` may be changed while keeping the same Venue identifier;
- deleting a Venue that has tickets is rejected with `409 Conflict`.

The `train_set_id` reference is logical only. There is no cross-database foreign key to Inventory.

### Ticket

A ticket identifies one seat on one concrete Venue/run.

```text
id
name
creation_date
venue_id
carriage_number
seat_number
refundable
type
```

`carriage_number` and `seat_number` are copied from the Inventory snapshot when the ticket is created. This is intentional: a ticket must preserve the passenger-facing place identity even though the source inventory document is versioned separately.

Inventory currently defines `seat_number` as `VARCHAR(3)`. `carriage_number` is the passenger-facing carriage number from `train_set_carriages`; its current Inventory type is `VARCHAR(16)`.

The database enforces:

```sql
UNIQUE (venue_id, carriage_number, seat_number)
```

Therefore one seat can have multiple tickets across different Venues/runs, but at most one ticket for the same seat on the same Venue.

There is intentionally **no Ticket status**. Booking/sale/refund state belongs to another service.

### Ticket name

`name` is a human-readable ticket description. It is optional in the create request, but the stored value is always non-null.

When omitted, the service generates:

```text
Билет: {seat_number}, вагон: {carriage_number} рейс: {venue_name}
```

When supplied, the explicit value is preserved.

### Ticket type

The allowed values are:

```text
VIP
USUAL
CHEAP
```

The value is nullable.

### Refundable

`refundable` is nullable because that matches the original lab model.

## Prices

Price information is intentionally not duplicated in `tickets`.

The master collection is:

```text
price_histories
----------------
ticket_id
changed_date
base_price
discount
```

`changed_date` is a timestamp (`TIMESTAMPTZ`) because several changes may occur on the same calendar date.

The current price state of a ticket is the latest `price_histories` row ordered by `changed_date DESC`.

`base_price` is nullable to preserve the original model's nullable `price` semantics; when present it must be greater than zero. `discount` is required and must be in the range `1..100`.

Creating a Ticket creates the initial price-history row from the price fields in the Ticket create request. Later price changes are represented by creating another `price_histories` row.

`price_histories` therefore supports only:

```text
POST
GET collection
GET by id
```

There is intentionally no `PUT` or `DELETE` for price history because changing or deleting historical records would destroy the meaning of the history. This is a deliberate extension beyond the old CRUD-only resource shape.

## Inventory CDC

Tickets consumes the Redpanda topic:

```text
inventory.train_set_snapshots
```

and stores the received snapshot using the same structure as the Inventory source CDC table:

```text
train_set_cdc
-------------
train_set_id INTEGER
 data        JSONB
version     BIGINT
```

The primary key is:

```text
(train_set_id, version)
```

The service keeps versions rather than overwriting the document. Kafka offsets are committed only after a successful database insert, and `(train_set_id, version)` makes replay idempotent.

The current Inventory snapshot contains the train set and its carriages, including:

- train-set fields (`id`, `code`, `name`, `buildNumber`, etc.);
- `carriages[]`;
- passenger-facing `carriageNumber`;
- physical carriage `position` inside the train set;
- carriage type data;
- scheme data;
- `seatPositions[]`;
- `seatNumber` for every seat.

`position` is the carriage order in the train-set composition. `carriageNumber` is the passenger-facing displayed number. They must not be confused.

The Inventory snapshot is currently self-contained, so Tickets does not need direct access to the Inventory database.

## Seat validation

When a Ticket is created or its place is changed, the application resolves:

```text
Venue -> train_set_id -> latest available train_set_cdc snapshot
```

Then it checks that the requested pair exists:

```text
carriageNumber
seatNumber
```

If the seat does not exist in the selected train set snapshot, the request fails with `400 Bad Request`.

The application-level check provides semantic validation. The relational unique constraint provides the final concurrency guarantee for duplicate tickets.

## Read-only Inventory resources

The following resources are projections from the JSON document rather than independent domain tables.

### Train sets

```http
GET /api/v1/tickets/train-sets
GET /api/v1/tickets/train-sets/{trainSetId}
```

The collection is paginated and supports sorting and filtering.

The logical response is derived from the latest stored snapshot for each `train_set_id`.

### Train-set carriages

```http
GET /api/v1/tickets/train-sets/{trainSetId}/carriages
```

The result is derived from `carriages[]` in the selected/latest train-set snapshot.

Supported fields include the carriage identifier, passenger-facing `carriageNumber`, physical `position`, inventory number, serial number and carriage type metadata.

### Seats

```http
GET /api/v1/tickets/train-sets/{trainSetId}/carriages/{carriageNumber}/seats
```

The result is derived from `scheme.seatPositions[]` for the selected carriage.

`seatNumber` remains a string of up to 3 characters, for example `1A`, `1B` or `12F`.

All collection GET endpoints use the common pagination/sorting contract.

## Common pagination response

Collection responses use the same shape as the original lab API:

```json
{
  "content": [],
  "page": 1,
  "size": 20,
  "totalElements": 125,
  "totalPages": 7,
  "hasNext": true,
  "hasPrevious": false
}
```

Pages are one-based. The default page is `1` and the default size is `20`; the implementation should cap the maximum page size at `100`.

`sort` uses the form:

```text
sort=field,asc
sort=field,desc
```

Multiple sort values may be supplied by repeating the query parameter.

The service must reject unknown sort fields instead of concatenating unchecked values into SQL.

## Special collection operations

The original lab requires three operations in addition to CRUD/search.

### Average discount

```http
GET /api/v1/tickets/tickets/discount/average
```

Calculates the average value of `discount` across all Tickets, using the latest price-history row of each ticket.

If the Ticket collection is empty, return `404 Not Found`.

### Latest Ticket

```http
GET /api/v1/tickets/tickets/latest
```

Returns any Ticket whose `creationDate` equals the maximum `creationDate` across the collection.

If the collection is empty, return `404 Not Found`.

### Tickets below discount

```http
GET /api/v1/tickets/tickets/by-discount-below/{discount}
```

Returns the Tickets whose current discount is strictly less than the requested value.

The operation accepts normal collection query parameters for pagination/sorting/filtering in the current API contract.

## Error handling

Business errors are JSON objects using a common structure:

```json
{
  "code": "TICKET_NOT_FOUND",
  "message": "Ticket 42 was not found",
  "timestamp": "2026-09-21T20:00:00Z",
  "path": "/api/v1/tickets/tickets/42"
}
```

Expected status mapping:

| Status | Meaning |
|---|---|
| `400` | Invalid path parameter, body validation failure, invalid enum, invalid pagination/sort/filter value, or requested seat does not exist in the selected train-set snapshot |
| `404` | Requested Ticket/Venue/price-history/train-set/carriage was not found, or a required collection-level special operation has no objects |
| `409` | Duplicate Venue name, duplicate `(venue_id, carriage_number, seat_number)`, illegal Venue train-set change, or another state conflict |
| `500` | Unexpected server/database failure |

The service should not expose SQL exception text directly to API consumers.

## Deletion semantics

Tickets:

```text
DELETE ticket -> deletes its price history through ON DELETE CASCADE
```

Venues:

```text
DELETE venue with no tickets -> allowed
DELETE venue with tickets    -> 409 Conflict
```

Price histories are not independently deleted.

## Source of truth summary

```text
Ticket fields            -> tickets database
Venue fields             -> tickets database (temporary master)
Price / discount         -> price_histories in tickets database
Train-set composition    -> inventory service
Train-set lifecycle      -> inventory service
Carriage / scheme / seat -> inventory service
Schedule / run identity  -> future schedule-service
Ticket lifecycle/status  -> future dedicated service/domain
```

This keeps ownership explicit while allowing the educational JAX-RS/WildFly service to operate independently of the not-yet-implemented Schedule service.
