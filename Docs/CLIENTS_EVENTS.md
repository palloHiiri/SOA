# Clients Kafka events

## 1. Event routing

The previous RabbitMQ exchanges/queues/shovels are replaced by Kafka topics. `clients` consumes the same topics directly.

```text
sso-ident
  ├──> sso.ident.user_registration.clients
  └──> sso.ident.verification_codes.(sms|email)

PostgreSQL CDC
  └──> Debezium Kafka Connect
          └──> sso.ident.user_updates.clients

clients consumes:
  sso.ident.user_registration.clients
  sso.ident.user_updates.clients
```

---

## 2. Registration event

Producer:

```text
sso-ident
```

Topic:

```text
sso.ident.user_registration.clients
```

Example payload:

```json
{
  "event": "SSO_IDENT_USER_REGISTERED",
  "userId": "2e59ac8b-5d3f-43b4-8f0c-4f83e6ab1db3",
  "username": "ivanov",
  "email": "ivan@example.com",
  "firstName": "Иван",
  "lastName": "Иванов"
}
```

The payload creates one `clients` row and one row in each 1:1 child table:

```text
clients
client_profiles
client_attributes
```

The registration consumer is idempotent by `clients.user_id UNIQUE`.

---

## 3. Identity update event

Source of the event:

```text
sso_ident_user_cdc
```

Produced by:

```text
Debezium PostgreSQL connector running on Kafka Connect
```

Debezium first uses the source topic derived from `topic.prefix=sso-ident` and then the `RegexRouter` SMT routes the record to:

```text
sso.ident.user_updates.clients
```

Example logical payload:

```json
{
  "user_id": "2e59ac8b-5d3f-43b4-8f0c-4f83e6ab1db3",
  "event_version": 42,
  "event_type": "USER_UPDATED",
  "email": "ivan.new@example.com",
  "username": "ivanov",
  "first_name": "Иван",
  "last_name": "Иванов",
  "updated_at": "2026-09-13T19:20:10Z"
}
```

Debezium uses `ExtractNewRecordState`, therefore consumers receive the CDC row rather than the complete Debezium envelope.

---

## 4. Verification code events

Verification events are published to one of two explicitly provisioned topics according to the event's `channel` field:

```text
sso.ident.verification_codes.sms
sso.ident.verification_codes.email
```

The current application uses the `email` channel for MFA and password-reset examples.

---

## 5. Version semantics

`event_version` is generated by:

```text
sso_ident_user_cdc_version_seq
```

The `clients` consumer stores it as:

```text
clients.identity_version
```

An incoming update is applied only when:

```text
incoming event_version > current identity_version
```

This protects against duplicate delivery and stale messages.

---

## 6. Why registration and update streams are separate

Registration is already a first-class SSO event and must create the client aggregate exactly once.

Identity updates are CDC events and may occur many times over the lifetime of a user.

Separate topics keep those responsibilities explicit and allow independent consumer scaling later:

```text
sso.ident.user_registration.clients
sso.ident.user_updates.clients
```

The `clients` service uses one Kafka consumer group (`clients`) for both streams, which gives the same practical one-consumer-per-service behavior the old queues provided.
